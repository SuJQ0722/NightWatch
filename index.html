TL;DR

Computer-use agents look at the screen on their own clock: take a screenshot, reason, act, sleep for a fixed delay, repeat. On a live screen this goes wrong both ways. The agent reasons about a screen that has already changed, and it sleeps through a page that loaded long ago. NightWatch lets the screen decide when the agent looks. A 0.8B watcher reads the screen as a stream and, through three fixed rules, interrupts reasoning that a change has made obsolete, voids a click whose target is gone, and wakes the agent the moment the screen settles. The agent itself is not modified.

Three proactive interventions

Interrupt

during reasoning

A dialog, an error or a new page appears while the agent is still reasoning about the old screen. NightWatch cancels the generation, and the agent re-plans on the current screen.

Void

before dispatch

The element the agent chose to click has moved, been covered, or disappeared. NightWatch discards the action before it lands, instead of letting it hit the wrong target.

Wake

after execution

The fixed sleep after each action is replaced: NightWatch wakes the agent as soon as the screen has settled, learned from hindsight labels rather than from stillness alone.

How it works

Results

Big model thinks, small model watches

NightWatch splits the work between two models that run at different speeds, like System 2 and System 1.

The agent · System 2

A large vision-language model (MiMo-V2.6-Flash, Qwen3.8-27B, ...) plans and acts. It is slow: one step takes seconds of reasoning, and it sees the screen only through the screenshots it asks for. NightWatch does not change it: same model, prompt and action space.

The watcher · System 1

NightWatch-0.8B is a Jev-style System-1 decision model. It reads the latest frames and the pending action once and returns a probability for every question of a fixed bank (has a dialog appeared, is the target still there, has the screen settled), without generating text, so it can keep up with the screen.

How they work together. The watcher never chooses what the agent does; it only decides when the agent should look and whether its current thought or action still holds. Fixed thresholds turn its answers into the three interventions: interrupt the agent's reasoning when the screen changes under it, void an action whose target has gone, and wake the agent as soon as the screen has settled. The small model keeps the large one in sync with the screen at a fraction of its cost: in the paper's ablation, the 0.8B watcher is faster and more successful than a hosted Jev API watcher and than a System-1 decision model more than 30× its size.

FAQ

What problem does NightWatch solve for computer-use agents?

GUI agents perceive the screen through discrete screenshots on their own clock, so they reason about screens that have already changed (stale actions) and sleep through screens that are ready (idle waiting). NightWatch lets the screen decide when the agent looks.

Do I need to change my agent, model or prompt?

No. NightWatch sits in the harness: it cancels the agent's model call, drops a pending action, or ends a wait. The agent's model, prompt and action space stay unchanged.

How is NightWatch related to Jev?

NightWatch-0.8B is a Jev-style System-1 decision model: like Jev, it answers a set of typed questions with probabilities in a single pass instead of generating text, which is what makes watching every frame cheap. In the paper it is compared with the hosted Jev API used as the watcher.

Which benchmarks and agents were evaluated?

OSWorld-Verified (100 tasks, 3 runs) and DynaCU-Bench (49 dynamic web tasks, 3 runs), with MiMo-V2.6-Flash and Qwen3.8-27B agents, against Vanilla, AOI and PUSV under the same screenshot-only input.

Can I use it in my own agent framework?

The code and the 0.8B watcher are open (Apache-2.0). A plugin for Hermes Agent's computer use is in preparation.
